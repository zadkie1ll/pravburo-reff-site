# План: перенос фронтенда site на React

Статус: все этапы выполнены. Осталась финальная проверка перед выкаткой (см. раздел «Этап 5»).
Область: только `pravburo-reff-site` (bounty и crm не трогаем).

## Цель

Заменить серверный рендер (Jinja2 + ванильный JS) на современный SPA-фронтенд
на React + TypeScript. Попутно навести порядок: разбить CSS, вынести повторяющиеся
элементы в компоненты, убрать дублирование логики в шаблонах.

Что **не** меняется: дизайн, тексты, бизнес-правила, авторизация и сессионные
куки, схема БД, интеграции (Telegram, Яндекс, Turnstile, push).

## Принципы

1. **Постепенно.** Старые страницы работают, пока новые не готовы. Переключаем
   маршрут за маршрутом, откат всегда возможен.
2. **Один этап за раз.** Каждый этап заканчивается рабочим состоянием и проверкой.
3. **Дизайн сохраняем.** Текущий `app.css` переносим, разбивая по смыслу; никакого
   редизайна и смены UI-библиотеки.
4. **CSP не ослабляем.** `style-src 'self'`: никаких inline `style=` и `style={{}}`,
   стили только классами.
5. **Безопасность бэкенда не трогаем.** Сессия, роли, 2FA админа, проверки доступа
   остаются на сервере; React только показывает.
6. **Git и деплой ведёт владелец проекта.** Мы готовим изменения, коммитит и
   выкатывает он.

## Как раздаём

Vite собирает статику в `frontend/dist`. FastAPI отдаёт её с того же домена
(так куки и сессия работают без изменений, CORS не нужен). Неизвестные пути
(не `/api`, не `/internal`, не `/static`) отдают `index.html` для React Router.

Dockerfile становится multi-stage: стадия Node собирает фронт, финальный образ
Python копирует `dist`. Nginx-конфиг в `deploy/` проверяем отдельно.

Для разработки: Vite dev-сервер на отдельном порту с proxy на бэкенд.
Работающий сервер на 8040 не трогаем.

## Бэкенд: что нужно добавить

Сейчас роуты отдают HTML и принимают form-POST с редиректом. Для React нужен
JSON-слой `/api/...` поверх **тех же сервисов** (`src/services/*`), чтобы не
дублировать бизнес-логику:

- `GET /api/me`: роль, id агента, признак onboarding/preview.
- Единый формат ошибок (код, сообщение, поля формы).
- 401 → редирект на вход, 403 → страница «нет доступа», 2FA-шаг для админа.
- POST-эндпоинты для каждой формы, что сейчас обрабатывается редиректом.
- Защита от CSRF для JSON-запросов (проверить текущее состояние и решить).
- Telegram и Яндекс callback остаются серверными редиректами.

Старые HTML-роуты удаляем только на финальном этапе.

## Риски

| Риск | Что делаем |
|---|---|
| CSP ломается от inline-стилей | Только классы, проверка консоли на каждом этапе |
| Расхождение поведения форм (редиректы → JSON) | Бизнес-логика остаётся в сервисах, API её только вызывает |
| Telegram/Яндекс-вход | Оставляем серверные callback, меняется только точка входа |
| Service worker кэширует старый фронт | Проверить `sw.js` и стратегию кэша до включения React |
| Регресс безопасности сессий | Куки и проверки ролей не меняем |

## Договорённости по API (этап 1)

- Ошибки: `{"error": {"code", "message", "fields"}}`, класс `ApiError` (`src/web/api_errors.py`).
- Доступ: `ApiAgent` / `ApiAdmin` (`src/web/api_dependencies.py`), вместо редиректа 303 отдают
  401 `unauthorized`, 403 `forbidden`, 403 `onboarding_required`.
- Изменяющие запросы: зависимость `CsrfProtected`, заголовок `X-CSRF-Token`.
- Фронтенд: `apiGet/apiPost/apiPut/apiDelete` (`shared/api/client.ts`), guard `RequireAuth`.

## Хвосты этапа 2

- Ошибки Telegram/Яндекс-callback пока рендерят старый `login.html`; после миграции всех
  auth-страниц заменить на редирект `/login?error=...` (React уже читает `?error=`).
- Старые form-роуты `/login`, `/register`... и их тесты удалить на этапе 5.
- Безопасность (расхождение со старым кодом): после подтверждения регистрации и сброса пароля
  старые роуты пускали админа в сессию **без 2FA**. Новые JSON-эндпоинты отправляют админа
  через шаг 2FA, как при обычном входе. Старые роуты не меняли: решено закрыть это на этапе 5, когда они удалятся.
- Безопасность (профиль): старый `POST /profile/email` кладёт **код подтверждения открытым
  текстом в сессионную куку** (она подписана, но не зашифрована: владелец читает код и может
  подтвердить чужой адрес). Новый `/api/v1/site/profile/email` хранит только HMAC кода
  (`session_secret`). Старый роут не менялся, уйдёт на этапе 5.
- Остаётся и в новом коде: счётчик попыток (5) лежит в той же куке, значит его можно обойти,
  повторно отправляя старую куку. Лимит nginx (10 запр/с) и TTL кода (10 мин) ограничивают
  подбор примерно 6 000 попыток из 1 000 000. Настоящее решение: хранить попытки на сервере
  (в БД), отдельная задача.

## Заметки по реферальной форме (этап 3)

- Открытие формы = один визит ссылки (так было и на старой странице: `GET /r/{code}` писал
  визит). Теперь визит пишет `GET /api/v1/site/referral/{code}`, его вызывает React один раз за
  просмотр. Боты без JavaScript визитов больше не создают.
- Форма анонимная, CSRF нет (как раньше): защита Turnstile + honeypot + лимит по IP. Боты, лимит
  и капча получают один и тот же ответ 429.
- Проверено вживую с публичными тестовыми ключами Cloudflare (`1x00000000000000000000AA`).
